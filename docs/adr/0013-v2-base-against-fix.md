# ADR 0013: V2 compares the target's tests on the base and on the fix, minus the tests that assert the flaw

- **Status:** Accepted
- **Date:** 2026-11-12
- **Step:** F3.5 (part B1)

## Context

The Blue Team's second verifier (V2) was written as "the target's server tests green, plus a regression test derived from the PoC". Juice Shop's own suite cannot be green under a real fix: it asserts its vulnerabilities as expected behaviour. `test/api/basket.test.ts` expects a 200 when a user reads another user's basket ("GET existing basket of another user") and when an order with a negative total is placed. On the clean source, 24 of its 951 tests already fail in the sandbox (they need the internet, or the `vuln-code-snippet` comments Janus strips, ADR 0012).

## Decision

V2 runs the target's tests twice, on the fix's base and on the fix, each file in its own process in the Dockerfile's `tests` stage without network, and judges them by code (`judgeTests`):

- **A regression test generated by code from the PoC** (`juiceShopRegressionTest`, never an LLM) is added to both runs. It must fail on the base, or it proves nothing, and pass on the fix.
- **No test that passed on the base may fail or vanish on the fix**, except the tests listed in `config/vulnerability-tests.yaml` for the finding's endpoint: tests that assert that very flaw. The list is written by hand, read only by the orchestrator, and never shown to an agent.
- Tests that already fail on the base are ignored. A fix V2 rejects is undone and the next iteration is told which tests broke.

## Alternatives considered

| Option                                         | Why not                                                                                                     |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| The target's suite green, as written           | Impossible on Juice Shop: its tests assert its vulnerabilities, so every real fix fails.                    |
| Base against fix, a human reviews new failures | V2 would never pass on its own for the reference findings, so the loop could never close a finding.         |
| Only the regression test                       | Misses fixes that break other features; in its first run V2 caught exactly that (the wallet test, F3.5-B1). |

## Consequences

- **Positive:** V2 measures what matters (the flaw is gone, nothing else broke) and it caught a real regression the first time it ran on the negative quantity. Runs are reproducible: one process per file, without `--test-force-exit`, which ended files before all their tests registered and made counts vary between runs.
- **Negative:** the list must be maintained per target and endpoint, and a wrong entry would hide a real regression; it is short and reviewed in the PR. Running the suite twice takes about 5 minutes per fix.
- **Follow-ups:** regression tests exist for the IDOR and negative-quantity PoCs; other kinds fail V2 closed until they get one.
