# ADR 0018: The benchmark counts Juice Shop's own solved challenges, against a fixed denominator

- **Status:** Accepted
- **Date:** 2026-11-13
- **Step:** F3.11

## Context

F3.11 publishes how much of OWASP Juice Shop the Red Team solves. The Red Team's engine is deterministic and generated by code (ADR 0011): every class attacks one thing, so its recall is bounded by what it was programmed to try, and the project rule is to publish the number with its interval, the unflattering part included (VISION: honest numbers).

Scoring has three traps. A recall over only the challenges the engine tries is 100 % by construction. A challenge Juice Shop marks solved may have been solved by something other than an attack. And Juice Shop's list of challenges is its own ground truth, which no agent may read.

## Decision

- **The score is Juice Shop's own count.** After each round the orchestrator reads `/api/Challenges` (never an agent: the guard that reads it is the orchestrator's, and every agent's scope excludes the path) and takes what the target marks solved. Janus does not say which request solved a challenge.
- **The denominator is fixed in config, not chosen by results.** `config/benchmarks.yaml` maps each Juice Shop category in which a Red Team class acts to those classes. Every challenge of those categories counts, solved or not and tried or not: 60 challenges in six categories for Juice Shop v20.3.0. A category with no challenge in the target is an error, so a renamed category cannot silently shrink the denominator.
- **The five reference challenges are reported apart** (the ones the oracles were built around in F3.2), never in place of the whole.
- **Every round is a fresh instance, after a control.** Each attack round starts its own container from the pinned image and tears it down. A control round does everything but attack (it starts the image, verifies ownership and reads the challenges). What the control has solved counts for no one and is listed. What is solved outside the categories is listed and never counted.
- **Side effects stay counted and are declared.** If Juice Shop marks a challenge solved because of a Janus request that was not aimed at it, the config says why (`sideEffects`), and the report gives the recall both with and without it. Counting is right because a Janus request did solve it; hiding it would be wrong.
- **Intervals:** a Wilson interval (`@janus/stats`) per round over the `n` challenges. The rounds repeat a deterministic engine, so they are expected to agree.
- **No model is called.** The benchmark's rounds pass the engine a gateway that fails if it is ever used. Cost is the sandbox's time.
- **Not done:** Nuclei, ZAP baseline and the Argus subset (optional in the roadmap). The first two crawl the target and would read its ground truth, and none of the three is an approved dependency.

## Alternatives considered

| Option                                                  | Why not                                                                                                     |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Recall over the five reference challenges only          | 100 % by design: it measures that the tests pass, not how much the engine finds.                            |
| Recall over all 116 challenges                          | It would say little about the Red Team: most categories (cryptography, deserialization, XXE) have no class. |
| Credit a challenge only when a Janus finding matches it | Needs a hand-made map from findings to challenges, and Juice Shop's count would stop being the evidence.    |
| Drop a side effect from the count                       | It would hide that a probe solved something; it is better to count it and say so.                           |

## Consequences

- **Positive:** one command regenerates a table with its command, image digest and commit; the number cannot be raised by choosing the denominator; a bug in the engine that solves something by accident shows up as a declared side effect instead of a silent gain.
- **Negative:**
  - The recall is low by design (6 of 60, 10 %), and the report says so.
  - The denominator mixes challenges no class could ever try with challenges one could: the per-category and per-challenge tables are how a reader tells them apart.
  - Side effects are found by hand: someone has to ask why a challenge outside the reference set was solved.
- **Follow-ups:**
  - The engine treats `POST /api/Users` as a login (the surface map shows no repeat-password parameter); that is the declared side effect, and fixing the generator is a separate step.
  - New classes raise the recall by adding generators (ADR 0011), not by touching the scoring.
