# Security policy

## Responsible use

Janus Arena includes offensive modules (a Red Team engine that attacks a target in a sandbox).
They exist to test software **you own or are authorised to test**, and they are built to refuse
anything else:

- **No scope, no attack.** An offensive module starts only with a verified `ScopePolicy`: the
  target proves ownership by serving a token at `/.well-known/janus-verify.txt`, and every request
  goes through a guard that enforces the allowed tests, the excluded paths and a rate limit
  (ADR 0005).
- **No internet egress.** Targets run in a Docker network with `internal: true`. The agents' browsers
  sit on that network and nowhere else.
- **No arbitrary code execution for agents.** Their tools are an allowlist. The Docker socket is
  never mounted into an agent or target container.
- **Attacks are generated by code, never by a model** (ADR 0011), and succeed only when a
  deterministic oracle says so.
- **Test data only.** Personas, accounts and seeds are synthetic.
- **Humans decide.** Janus never merges and never approves a pull request.

Do not point Janus at systems you do not own. The scope configuration (`config/scopes.yaml`) and
the guard are there to stop mistakes, not to authorise misuse; using the code against a third
party's systems is your responsibility alone.

## Reporting a vulnerability in Janus

If you find a way to make Janus act outside its scope (for example, bypassing the guard, escaping
the sandbox network, or reading a target's ground truth from an agent), please report it
privately: open a **private security advisory** on this repository (Security → Report a
vulnerability) rather than a public issue. Include the commit, what you did and what happened.

This is a research project maintained in spare time: expect an answer within a few days, not hours.
